# oingg-bff-ts 資料邊界架構決策記錄

> 這份文件原本是一份通用的企業架構理論報告，2026-08-31 第一次改寫成記錄 oingg-bff-ts 真實案例的版本。當天稍晚使用者又進一步糾正了第一次改寫的結論本身——「原則一」（原始值可以直連後台 DB）被推翻，改成一條更嚴格的鐵律。這是第二次改寫，反映最終結論；第一次改寫版本的推導過程保留在 git 歷史裡，不重複貼在這裡，避免舊結論被誤讀成現行原則。

## 定位：三層架構，不是兩層

之前的版本只分「中台（bff-ts）」跟「後台」兩層，這是錯的。正確的架構是三層：

| 層級 | 服務 | 職責 |
| :---- | :---- | :---- |
| **前台** | oingg-web-nuxt | 使用者介面 |
| **業務中台**（Business Middle-Platform） | **oingg-bff-ts**（本專案） | 使用情境組裝——使用者偏好、篩選條件、顯示欄位、認證授權。**自己只擁有使用者自己的資料**（users/holdings/transactions/watchlist/theme 偏好/screener 與 column presets）。 |
| **數據中台**（Data Middle-Platform） | **oingg-analysis-ts** | 鏡像/彙整所有後台的原始與計算過資料，是業務中台唯一被允許存取的對象。 |
| **後台** | oingg-twse-ts、oingg-tpex-ts、oingg-mops-ts、oingg-gov-ts、oingg-sitca-ts | 各自擁有原始資料的擷取與存放（股價、財報、總經數據…），不直接服務業務中台。 |

## 唯一鐵律

> **業務中台（bff-ts）永遠不能主動存取後台，不管是直連 DB 還是呼叫 API。bff-ts 唯一被允許存取的外部服務是 oingg-analysis-ts（數據中台）——而且必須透過它的 API，連 analysis-ts 自己的 DB 都不能直連。**

這條規則的來源是使用者的明確糾正：「後台永遠不接業務中台，也就是你存取 TPEX 絕對是錯的」，並確認範圍——「以後絕對不可以打後台，只可以打數據中台的資料，數據中台會有後台的資料鏡像備份。」

**這推翻了原本文件裡的「原則一」**（原始值、無運算的直連 DB 可以接受）。原則一原本用 `stock.service.ts` 直查 twse/tpex、`screener.service.ts` 直查 analysis-ts 的 DB 當作「可接受的取巧」——兩者都不成立：前者是直接碰後台（絕對禁止），後者是繞過 analysis-ts 的服務邊界直連它的 DB（也是禁止的，只是禁止的對象剛好是唯一允許互動的服務）。

**目前違反這條鐵律、需要修復的地方**——見 [直連DB反模式修復計畫.md](./直連DB反模式修復計畫.md)：
- `stock.service.ts` 直查 twse-ts／tpex-ts 的 `daily_price`／`daily_valuation`。
- `screener.service.ts` 直查 analysis-ts 自己 DB 裡的 30+ 張指標表。

## 仍然成立的原則（沒有被推翻）

### 二次加工（衍生運算）→ 必須交給 analysis-ts，不能自己重做一份

排序、TOP-N、排除規則、合併多來源資料是業務邏輯，不是查詢。這條原本就符合新鐵律（呼叫 analysis-ts 的 API），不受這次修正影響。

**案例**：首頁排行卡片一開始被實作成直接查 twse/tpex 做排序＋合併，使用者糾正：「排行應該算是對資料二次加工，所以由 Analysis 處理很合理……bff 抓 Analysis 現有的資料就好」，改回呼叫 analysis-ts 的 `GET /valuation/ranking`（[valuationRanking.client.ts](../src/domains/screener/valuationRanking.client.ts)）。這是目前唯一完全合規的跨服務資料存取範例——**之後任何新的跨服務存取都應該長得像這支 client**：只呼叫 analysis-ts、fetch 失敗轉乾淨的 502、回應格式驗證後才回傳。

### 目錄/中繼資料 → 「異動方主動通知，被通知方才去拉取」

filter catalog 的同步機制符合新鐵律——通知（`POST /filters/sync`）跟拉取（`GET /filters`）的對象都是 analysis-ts，沒有碰過任何後台。

**案例**：`filterCatalog.service.ts` 的 `syncFilterCatalog()`／`bootstrapFilterCatalogIfEmpty()`；認證用 `requireTaskSecret`（[requireTaskSecret.ts](../src/shared/requireTaskSecret.ts)，借用 oingg-twse-ts 已經驗證過的共用密鑰模式）。

**事故教訓**：這個同步機制曾經是每次啟動就 `deleteMany()` 全刪再 `createMany()` 全建，因為 `FilterMetricField` 被使用者儲存的 `ScreenerPresetFilter` 用 `onDelete: Cascade` 參照，每次重啟都把使用者存的篩選條件砍光。修法是改成用自然鍵 upsert，只刪真正消失的欄位（[filterCatalog.repository.ts](../src/domains/filterCatalog/filterCatalog.repository.ts) 的 `replaceFilterCatalog()`）。

### 沒有任何程式碼在用的存取，就該砍掉

**案例**：`MOPS_DATABASE_URL` 註冊了連線池但從來沒有程式碼查詢過，已從 `.env`／`.env.example`／`/system/health` 文件範例中移除。

**修正（原本這條寫錯了）**：舊版文件曾經寫「如果未來需要顯示月營收歷史圖表，可以直接查 mops-ts」——這在新鐵律下不成立。**任何 mops-ts 的資料，未來都只能透過 analysis-ts 取得，不管是原始值還是計算過的值。** 如果 analysis-ts 還沒有鏡像月營收原始歷史資料，那是 analysis-ts 需要擴充的範圍，不是 bff-ts 可以繞過去直接查 mops-ts 的理由。

## 已知的阻塞項：analysis-ts 對 twse/tpex 的鏡像目前不完整

新鐵律要求 bff-ts 的股價查詢也改打 analysis-ts，但 analysis-ts 自己 DB 裡對應的鏡像表 `valuation_market_ratios` 目前**只有 1 筆資料**（2026-08-31 查證）——這正是稍早這個 session 發現「排行榜不能用這張表」的同一個資料完整性問題，還沒解決。這代表：**在 analysis-ts 補齊 twse/tpex 原始資料的完整鏡像之前，bff-ts 沒辦法安全切斷對 twse/tpex 的直連**，切了會導致股價查詢從「幾乎所有股票都查得到」退化成「只有 1 檔查得到」。詳細修復順序見 [直連DB反模式修復計畫.md](./直連DB反模式修復計畫.md)。

## 決策速查表

| 資料 | 現況 | 是否合規 |
| :---- | :---- | :---- |
| 股票最新股價/估值 | bff-ts 直查 twse/tpex DB | **違規，待修復**（見遷移計畫） |
| 財報比率/量化分數原始值 | bff-ts 直查 analysis-ts DB | **違規，待修復**（見遷移計畫） |
| 排行榜（P/E、殖利率排序＋合併上市櫃） | 呼叫 analysis-ts `GET /valuation/ranking` | 合規 |
| filter catalog（分類/指標/欄位目錄） | analysis-ts 主動通知 → bff-ts 向 analysis-ts 拉取 | 合規 |
| 原始財報/月營收/股利分配（mops-ts） | 完全未存取 | 合規（維持現狀，未來若要用必須經 analysis-ts） |

## 附錄：相關技術落地

- 每個 Neon `pg.Pool` 都有明確的 `max`／`connectionTimeoutMillis`／`idleTimeoutMillis`（見「微服務資料庫連線最佳實踐」報告與 `pool.ts`）——修復完成後，這些 pool config 應該只剩 bff-ts 自己的 `DATABASE_URL` 還在用，`TWSE_DATABASE_URL`／`TPEX_DATABASE_URL`／`ANALYSIS_DATABASE_URL` 全部應該可以移除，比照 `MOPS_DATABASE_URL` 的做法。
- 共用密鑰驗證的 server-to-server 端點模式（`requireTaskSecret`）目前用在 `POST /filters/sync`；未來任何「後台/數據中台主動通知業務中台」的場景都可以複用同一套模式。
