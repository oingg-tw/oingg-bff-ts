# oingg-bff-ts 資料邊界架構決策記錄

> 這份文件原本是一份通用的企業架構理論報告（銀行/ERP/電商案例），跟 oingg 生態系無關。2026-08-31 全文改寫：拿掉抽象理論框架，改成記錄 oingg-bff-ts 這個中台在實際開發過程中，針對「什麼時候可以直連後台服務的 DB、什麼時候必須走對方 API」所做過的真實判斷——每一條原則後面都附上真的發生過的案例或事故，不是理論推導。之後每次遇到新的跨服務資料存取決策，先看這份文件有沒有對應原則；沒有的話，做完決策後回來補一條。

## 定位

**oingg-bff-ts** 是中台（BFF, Backend-for-Frontend）。它服務前端（oingg-web-nuxt），底下有四個「後台」服務，各自擁有自己的 DB、各自是自己那份資料的權威來源（source of truth）：

| 後台服務 | 擁有的資料 | bff-ts 目前的存取方式 |
| :---- | :---- | :---- |
| oingg-twse-ts | 上市股票每日股價/估值（`daily_price`／`daily_valuation`） | 直連 DB（唯讀） |
| oingg-tpex-ts | 上櫃股票每日股價/估值 | 直連 DB（唯讀） |
| oingg-analysis-ts | 財報比率/量化分數（算好的）、filter catalog 目錄、排行榜 | 部分直連 DB、部分呼叫 API（見下） |
| oingg-mops-ts | 原始財報（損益表/資產負債表/月營收/股利分配…） | 目前完全沒有存取（見原則四） |

## 核心原則

### 原則一：原始值，沒有二次加工 → 直連 DB 沒問題

如果 bff-ts 要的只是「這個表格裡的某一欄，原封不動」，不涉及排序、篩選規則、跨欄位運算，直接查對方的 DB 是可接受的——本質上跟叫用一支「查詢單筆資料」的 API 沒有本質差異，只是省了一層 HTTP。

**案例**：
- `stock.service.ts` 直接查 twse/tpex 的 `daily_price`（最新收盤價）、`daily_valuation`（PER/PBR/殖利率）——`getStockQuote()`、`getLatestClosePrices()`。
- `screener.service.ts` 直接查 analysis-ts 的「analysis」DB 裡的季報比率表（ROE、負債比、Altman Z-Score…）——每個指標一個 CTE，取「該股票最新一筆合併報表」，見 `analysisMetricTables.ts`。

### 原則二：二次加工（衍生運算）→ 必須交給算出資料的服務，不能自己重做一份

排序、TOP-N、排除規則、合併多來源資料——這些是「業務邏輯」，不是「查詢」。誰擁有原始資料，誰就該擁有這段邏輯；bff-ts 自己重寫一份，等於在中台裡複製了一份後台的業務規則，兩邊之後改一個地方就會不一致。

**案例（真實發生過的事故，不是假設）**：一開始 bff-ts 為了「首頁排行卡片」（P/E 最低、殖利率最高）自己寫了一段直接查 twse/tpex `daily_valuation` 做排序＋合併上市/上櫃的邏輯，理由是效能好、覆蓋率完整。後來使用者糾正：「排行應該算是對資料二次加工，所以由 Analysis 處理很合理……bff 抓 Analysis 現有的資料就好，你也比較可以維持 BFF 的定位，盡量少處理資料，多處理使用情境。」全部改回呼叫 analysis-ts 自己的 `GET /valuation/ranking`（[valuationRanking.client.ts](../src/domains/screener/valuationRanking.client.ts)），bff-ts 只做「你要看哪個排行、要不要多帶股價欄位」這種前端使用情境的組裝。

**判斷法**：如果這段邏輯「跟資料放在同一個地方就該一起維護」，就不該搬進 bff。

### 原則三：目錄/中繼資料 → 「異動方主動通知，被通知方才去拉取」，不是輪詢也不是被動接收推送

像 filter catalog 這種「不常變、但變了大家都要立刻知道」的中繼資料，三種做法都有問題：
- 每次啟動都主動去對方那邊拉一次 → 對方沒變也白拉，而且新資料要等下次重啟才會出現。
- 定期輪詢 → 大部分時間都在做白工，還多了一個要維護的排程。
- 對方直接把資料塞給你（data push）→ 你被迫信任對方送來的資料格式，且你不再是自己去驗證「這真的是最新的」，架構上跟直連資料庫犯的錯本質相同（喪失 single source of truth）。

bff-ts 採用的做法：**analysis-ts 異動後主動呼叫 `POST /filters/sync`（一個 server-to-server、帶共用密鑰的通知端點）**，bff-ts 收到通知後，自己去打 analysis-ts 的 `GET /filters` 重新拉一份完整目錄存進本地 DB。通知本身不帶任何目錄內容——這樣 analysis-ts 永遠是資料的權威來源，bff-ts 永遠只信任自己親自拉回來的資料。

**案例**：`filterCatalog.service.ts` 的 `syncFilterCatalog()`／`bootstrapFilterCatalogIfEmpty()`；認證機制 `requireTaskSecret`（[requireTaskSecret.ts](../src/shared/requireTaskSecret.ts)，借用 oingg-twse-ts 已經驗證過的共用密鑰模式：header/query 雙管道、伺服器未設定密鑰時 fail-closed、`timingSafeEqual` 防時序攻擊）。

**事故教訓**：這個機制原本是「每次啟動都全量同步」。同步邏輯本身也曾經是 `deleteMany()` 全刪再 `createMany()` 全建——因為 `FilterMetricField` 被使用者自己儲存的 `ScreenerPresetFilter`（篩選條件）以 `onDelete: Cascade` 參照，每次重啟都會把使用者存的篩選條件整個砍光，`ScreenerPreset` 本體還在、但 `filters` 變成空陣列。修法是改成「用自然鍵 upsert，只刪真的從目錄裡消失的欄位」（[filterCatalog.repository.ts](../src/domains/filterCatalog/filterCatalog.repository.ts) 的 `replaceFilterCatalog()`）——這正是舊文件警告過的「變更連鎖反應會刪掉不該刪的東西」，這裡真的發生過。

### 原則四：沒有任何程式碼在用的存取，就該砍掉，不要留著「以後可能用得到」

連線池、環境變數、殘留的權限——只要沒有實際查詢在用，就是純粹的耦合面積，沒有對應的好處。

**案例**：`MOPS_DATABASE_URL` 從專案一開始就註冊了連線池（`pool.ts` 會自動探索任何 `<NAME>_DATABASE_URL`），但查證後發現從來沒有任何一行程式碼真的查詢過它——純粹是「跟 twse/tpex 一起順手加上去」的殘留設定。已從 `.env`／`.env.example`／`/system/health` 的文件範例中全部移除。

**什麼情況會讓 bff-ts 未來需要直連 MOPS**：只有「原封不動顯示一段歷史時間序列、不需要挑『最新一筆』的業務邏輯」這種情境，例如月營收歷史圖表、股利發放歷史清單——跟 twse/tpex 的股價歷史查詢是同一種模式（見 [reference：MOPS 存取時機](../src/domains/stock/stock.service.ts) 的判斷邏輯）。任何需要「挑出某公司最新合併報表」這種邏輯的需求，都應該由 analysis-ts 處理，不該在 bff-ts 重新實作一次。

## 為什麼「跨服務直連 DB」在這裡是可接受的取捨，而不是教科書說的反模式

嚴格的微服務治理原則（Database-per-service、絕不共用資料庫）在企業級、多團隊、後台系統老舊龐雜的情境下是對的——但 oingg 生態系目前是單一開發者用多個 Claude session 同時維護的一組小型服務，彼此之間可以即時跨 session 溝通協調（例如本文件記錄的排行榜事故，就是即時被使用者糾正、當天就改完的）。在這個規模下：

- 原始值直連的耦合成本很低：schema 改動時，另一個 session 幾乎立刻就能發現並協調修正（本文件的 ROC 民國年 bug 就是一個活生生的例子——bff-ts 直接讀 analysis-ts 的 `year` 欄位時，一開始誤判成西元年，上線後才發現該欄位其實是民國年，透過即時查真實 DB 抓到並修正）。
- 效能上，直連省下的 HTTP 往返在小規模流量下是實際可感受到的差異；多一層 API 在目前規模下主要是架構上的乾淨，不是效能上的必要。

**但這是刻意的、有邊界的取捨，不是「怎麼方便就怎麼查」**：範圍嚴格限制在「原始值」（原則一），任何運算/排序/合併規則一律回到原則二。如果未來這個生態系規模變大（多人協作、後台 schema 變動頻率上升、或跨服務即時溝通不再可靠），應該重新評估，把直連的部分逐步收斂成 API 呼叫——尤其是原則一清單裡「涉及較複雜欄位對應規則」的部分（例如 `toSnakeCase()` 這種需要手動維護 camelCase→snake_case 對應規則、且已經因為 `beta1Y`／ROC 年份等邊界案例出過錯的邏輯），是這批直連中最先該收斂的候選。

## 決策速查表

| 資料 | 現況 | 對應原則 |
| :---- | :---- | :---- |
| 股票最新股價/估值（twse/tpex） | 直連 DB | 原則一 |
| 財報比率/量化分數原始值（analysis-ts） | 直連 DB | 原則一 |
| 排行榜（P/E、殖利率排序＋合併上市櫃） | 呼叫 analysis-ts `GET /valuation/ranking` | 原則二 |
| filter catalog（分類/指標/欄位目錄） | analysis-ts 主動通知 → bff-ts 主動拉取 | 原則三 |
| 原始財報/月營收/股利分配（mops-ts） | 完全未存取 | 原則四 |

## 附錄：相關技術落地

- 每個 Neon `pg.Pool` 都有明確的 `max`／`connectionTimeoutMillis`／`idleTimeoutMillis`，避免中台的高頻請求把後台的連線池耗盡（見「微服務資料庫連線最佳實踐」報告與 `pool.ts`）。
- 共用密鑰驗證的 server-to-server 端點模式（`requireTaskSecret`）目前用在 `POST /filters/sync`；未來任何「後台主動通知中台」的場景都可以複用同一套模式。
