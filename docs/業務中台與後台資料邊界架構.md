# oingg-bff-ts 資料邊界架構決策記錄

> 這份文件原本是一份通用的企業架構理論報告，2026-08-31 第一次改寫成記錄 oingg-bff-ts 真實案例的版本。當天稍晚使用者又進一步糾正了第一次改寫的結論本身——「原則一」（原始值可以直連後台 DB）被推翻，改成一條更嚴格的鐵律。這是第二次改寫，反映最終結論；第一次改寫版本的推導過程保留在 git 歷史裡，不重複貼在這裡，避免舊結論被誤讀成現行原則。

## 定位：三層架構，不是兩層

之前的版本只分「中台（bff-ts）」跟「後台」兩層，這是錯的。正確的架構是三層：

| 層級 | 服務 | 職責 |
| :---- | :---- | :---- |
| **前台** | oingg-web-nuxt | 使用者介面 |
| **業務中台**（Business Middle-Platform） | **oingg-bff-ts**（本專案） | 使用情境組裝——使用者偏好、篩選條件、顯示欄位、認證授權。**自己只擁有使用者自己的資料**（users/holdings/transactions/watchlist/theme 偏好/screener 與 column presets）。 |
| **數據中台**（Data Middle-Platform） | **oingg-analysis-ts** | 鏡像/彙整所有後台的原始與計算過資料，是業務中台唯一被允許存取的對象。 |
| **後台** | oingg-twse-ts、oingg-tpex-ts、oingg-mops-ts、oingg-gov-ts、oingg-sitca-ts | 各自擁有原始資料的擷取與存放（股價、財報、總經數據…），不直接服務業務中台。 |

## 兩條鐵律

> **鐵律一：業務中台（bff-ts）永遠不能主動存取後台，不管是直連 DB 還是呼叫 API。bff-ts 唯一被允許存取的外部服務是 oingg-analysis-ts（數據中台）——而且必須透過它的 API，連 analysis-ts 自己的 DB 都不能直連。**
>
> **鐵律二：數據中台（analysis-ts）不知道業務中台（bff-ts）存在。** 耦合方向永遠是單向的——bff-ts 可以知道並依賴 analysis-ts，但 analysis-ts 的程式碼不能持有 bff-ts 的密鑰、不能呼叫 bff-ts 的任何端點、不能因為 bff-ts 的需求而改變自己的行為。任何跨服務資料同步，發起方永遠只能是 bff-ts（拉取），絕不是 analysis-ts（推送/通知）。

這兩條規則都來自使用者的明確糾正。鐵律一：「後台永遠不接業務中台，也就是你存取 TPEX 絕對是錯的」，並確認範圍——「以後絕對不可以打後台，只可以打數據中台的資料，數據中台會有後台的資料鏡像備份。」鐵律二：在 bff-ts 已經跟 analysis-ts 協調好、驗證過 `POST /filters/sync` 這套推播通知機制之後才提出——「打 5000 去抓 /filters 的功能要加回來。數據中台不知道業務中台的存在。」代表即使雙方已經協調一致且運作正常，只要違反這條方向性原則，還是要拆掉重做。

**這推翻了原本文件裡的「原則一」**（原始值、無運算的直連 DB 可以接受）——`stock.service.ts` 直查 twse/tpex、`screener.service.ts` 直查 analysis-ts 的 DB 都不成立：前者是直接碰後台（鐵律一絕對禁止），後者是繞過 analysis-ts 的服務邊界直連它的 DB。

**也推翻了 filter catalog 原本的同步設計**（analysis-ts 異動後主動呼叫 `POST /filters/sync` 通知 bff-ts）——那套機制完全符合鐵律一（只跟 analysis-ts 互動），但違反鐵律二：analysis-ts 的程式碼因此持有 bff-ts 的 `TASK_SECRET`、知道 bff-ts 的 URL、會因為 bff-ts 的存在而多執行一段邏輯。已經整個拆除，改回 bff-ts 單向主動拉取（見下）。

**目前狀態**——見 [直連DB反模式修復計畫.md](./直連DB反模式修復計畫.md)：
- `stock.service.ts` 對 twse-ts／tpex-ts 的直連**已移除並修復完成**（2026-09-01）。改呼叫 analysis-ts 的 `GET /stocks/:symbol/quote`／`GET /stocks/prices`，`GET /stocks/:symbol` 恢復正常運作。
- `screener.service.ts` 直查 analysis-ts 自己 DB 裡的 30+ 張指標表——**尚未修復**，待規劃。

## 仍然成立的原則（沒有被推翻）

### 二次加工（衍生運算）→ 必須交給 analysis-ts，不能自己重做一份

排序、TOP-N、排除規則、合併多來源資料是業務邏輯，不是查詢。這條原本就符合新鐵律（呼叫 analysis-ts 的 API），不受這次修正影響。

**案例**：首頁排行卡片一開始被實作成直接查 twse/tpex 做排序＋合併，使用者糾正：「排行應該算是對資料二次加工，所以由 Analysis 處理很合理……bff 抓 Analysis 現有的資料就好」，改回呼叫 analysis-ts 的 `GET /valuation/ranking`（[valuationRanking.client.ts](../src/domains/screener/valuationRanking.client.ts)）。這是目前唯一完全合規的跨服務資料存取範例——**之後任何新的跨服務存取都應該長得像這支 client**：只呼叫 analysis-ts、fetch 失敗轉乾淨的 502、回應格式驗證後才回傳。

### 目錄/中繼資料 → bff-ts 單向主動拉取，analysis-ts 不知情

filter catalog 曾經改成「analysis-ts 異動後主動通知 bff-ts、bff-ts 才去拉取」的推播模式（`POST /filters/sync`，共用密鑰驗證），而且雙方已經協調對齊、實測過 round-trip 成功。**這個設計後來被推翻，原因是違反鐵律二**：analysis-ts 的程式碼因此需要知道 bff-ts 存在、持有它的密鑰、在自己更新 catalog 後多執行一段「通知 bff-ts」的邏輯——不管拉取本身的方向對不對，只要對方需要知道你存在，就違規。

現行做法：`startFilterCatalogSync()` 只在 bff-ts 自己啟動時，單方面向 analysis-ts 的 `GET /filters` 拉取一次，analysis-ts 對此完全不知情、不需要做任何事。代價是新鮮度只跟得上 bff-ts 自己的重啟頻率——這是接受的取捨，不是尚待解決的問題；如果之後需要更即時的更新，解法會是 bff-ts 自己排週期性輪詢，而不是恢復任何形式的 analysis-ts → bff-ts 通知。

**事故教訓**：這個同步機制曾經是每次啟動就 `deleteMany()` 全刪再 `createMany()` 全建，因為 `FilterMetricField` 被使用者儲存的 `ScreenerPresetFilter` 用 `onDelete: Cascade` 參照，每次重啟都把使用者存的篩選條件砍光。修法是改成用自然鍵 upsert，只刪真正消失的欄位（[filterCatalog.repository.ts](../src/domains/filterCatalog/filterCatalog.repository.ts) 的 `replaceFilterCatalog()`）。

### 沒有任何程式碼在用的存取，就該砍掉

**案例**：`MOPS_DATABASE_URL` 註冊了連線池但從來沒有程式碼查詢過，已從 `.env`／`.env.example`／`/system/health` 文件範例中移除。

**修正（原本這條寫錯了）**：舊版文件曾經寫「如果未來需要顯示月營收歷史圖表，可以直接查 mops-ts」——這在新鐵律下不成立。**任何 mops-ts 的資料，未來都只能透過 analysis-ts 取得，不管是原始值還是計算過的值。** 如果 analysis-ts 還沒有鏡像月營收原始歷史資料，那是 analysis-ts 需要擴充的範圍，不是 bff-ts 可以繞過去直接查 mops-ts 的理由。

## 已解決：analysis-ts 對 twse/tpex 的鏡像不完整問題

analysis-ts 自己 DB 裡對應的鏡像表 `valuation_market_ratios` 曾經**只有 1 筆資料**（2026-08-31 查證）——根因是 marketRatios job 查價格/估值時漏查了 tpex 的 `daily_valuation`，導致所有 TPEx 公司寫入被跳過。**2026-09-01 已修復並重跑全市場批次**，現在 twse+tpex 合計 2,092/2,092 全滿。analysis-ts 依此建好了 `GET /stocks/:symbol/quote`／`GET /stocks/prices?symbols=...`，bff-ts 已切換過去，`GET /stocks/:symbol` 恢復正常運作。詳細見 [直連DB反模式修復計畫.md](./直連DB反模式修復計畫.md)。

已知殘留資料缺口（analysis-ts 側，非架構違規）：`oingg-tpex` 的 `daily_price` 目前是空表，上櫃股票的 `quote.price` 暫時會是 `null`（`valuation` 有資料），等 tpex-ts 回補後自動修正。

## 決策速查表

| 資料 | 現況 | 是否合規 |
| :---- | :---- | :---- |
| 股票最新股價/估值 | 呼叫 analysis-ts `GET /stocks/:symbol/quote`／`GET /stocks/prices` | 合規 |
| 財報比率/量化分數原始值 | bff-ts 直查 analysis-ts DB | **違規，待修復**（見遷移計畫） |
| 排行榜（P/E、殖利率排序＋合併上市櫃） | 呼叫 analysis-ts `GET /valuation/ranking` | 合規 |
| filter catalog（分類/指標/欄位目錄） | bff-ts 啟動時單向向 analysis-ts 拉取，analysis-ts 不知情 | 合規 |
| 原始財報/月營收/股利分配（mops-ts） | 完全未存取 | 合規（維持現狀，未來若要用必須經 analysis-ts） |

## 附錄：相關技術落地

- 每個 Neon `pg.Pool` 都有明確的 `max`／`connectionTimeoutMillis`／`idleTimeoutMillis`（見「微服務資料庫連線最佳實踐」報告與 `pool.ts`）——`TWSE_DATABASE_URL`／`TPEX_DATABASE_URL` 已移除；`ANALYSIS_DATABASE_URL` 待 screener/ranking 遷移完成後也應該移除，屆時只剩 bff-ts 自己的 `DATABASE_URL`。
- 共用密鑰驗證的 server-to-server 端點模式（`requireTaskSecret`）**已經整個移除**——因為它唯一的用途（`POST /filters/sync`）違反鐵律二。這套模式本身沒有錯，只是這個生態系裡沒有任何「後台/數據中台需要主動通知業務中台」的合法場景；如果之後真的需要一個服務主動通知另一個服務，且方向是 bff-ts 通知別人（而不是別人通知 bff-ts），可以重新考慮這個模式。
