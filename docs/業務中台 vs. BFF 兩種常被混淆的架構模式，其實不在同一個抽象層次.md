# 業務中台 vs. BFF：兩種常被混淆的架構模式，其實不在同一個抽象層次

## TL;DR
- **業務中台（Business Middle Platform）與 BFF（Backend for Frontend）解決的是不同層次的問題，兩者不是競爭關係，而是可以共存於同一架構**：業務中台是「向多個前台複用核心業務能力」的組織與應用架構（阿里巴巴「大中台、小前台」戰略的產物），BFF 則是「為單一前端量身打造聚合層」的技術架構模式（源自 SoundCloud）。
- **最關鍵的區別在「服務對象」與「擁有的東西」**：業務中台被「多個」業務線／前台共享、擁有核心業務領域邏輯（訂單、用戶、支付等可複用能力）；BFF「專屬於單一前端」（web 一個、mobile 一個）、只做聚合／裁剪／視圖塑形／協定轉換，不擁有核心業務邏輯。
- **對你的 oingg.com 架構而言最務實的結論**：「數據中台 + 業務中台」是後端能力沉澱層，而每個前端（Vue web、未來的行動端）應各自擁有輕薄的 BFF（用你熟悉的 Node.js/TypeScript 實作最合適），BFF 向業務中台取數並塑形，切勿讓 BFF 累積業務邏輯、也切勿把業務中台做成只服務單一前端的胖 API。

## Key Findings

1. **兩者不在同一抽象層次**。中台社群的權威整理指出：「BFF 更多是技術架構層面，中台更多是在應用架構層面」，且「BFF 往往是專注於服務一個前台；而中台的特點就是通過抽象後可以同時服務多個前台」。這是釐清兩者最核心的一句話。

2. **業務中台的核心意圖是「企業級業務能力複用」**。它源自阿里巴巴 2015 年 12 月 7 日張勇內部信正式啟動的「大中台、小前台」戰略，目標是把分散在不同渠道、業務場景中重複建設的業務能力，沉澱成企業級中台業務模型，面向所有業務場景實現「能力複用與流程融合」，最大限度減少「重複造輪子」。

3. **BFF 的核心意圖是「為特定 UI 聚合／裁剪，降低前端複雜度」**。Sam Newman 的定義是「一個使用者體驗，一個後端」（one backend per user experience），BFF「緊耦合於單一使用者體驗，且通常由維護該使用者介面的同一團隊維護」（the BFF is tightly coupled to a specific user experience, and will typically be maintained by the same team as the user interface），用來解決通用 API 後端面對多端時「過度抓取／抓取不足」與釋出瓶頸的問題。

4. **範圍不同**：業務中台是「一對多」（一套能力服務多個前台，內部像多租戶）；BFF 是「一對一」（一個前端類型一個 BFF）。Sam Newman 引用的準則是「one experience, one BFF」。

5. **擁有物不同**：業務中台擁有並封裝核心業務領域模型與規則（常用 DDD 限界上下文建模，落地為微服務）；BFF 只做聚合、轉換、協定轉換，業務邏輯應留在下游服務——「A BFF that accumulates business rules becomes a maintenance liability」。

6. **團隊歸屬不同**：業務中台由平台／核心團隊擁有，服務多個產品團隊；BFF 由該使用者介面的同一團隊維護，即由前端／該客戶端團隊擁有。

7. **兩者可以共存**：典型分層是「前端 App → BFF（每前端一個）→ API 網關 → 業務中台（可複用業務能力）→ 數據中台／基礎設施」。這正是騰訊雲、好未來等公司的實際落地方式。

8. **中台戰略近年遭遇重大反思與「拆中台」浪潮**。阿里在 2023 年 3 月的「1+6+N」改組後，把業務中台併入淘天集團、數據中台獨立為愛橙技術，「大中台」制度成為歷史；字節跳動、京東等大廠亦相繼弱化中台。這是採用中台思維前必須認知的重要背景。

## Details

### 一、業務中台（Business Middle Platform）

**起源與意圖。** 中台戰略的官方起點是 2015 年 12 月 7 日，時任阿里巴巴集團 CEO 張勇（逍遙子）發出內部信，宣布：「今天起，我們全面啟動阿里巴巴集團 2018 年中台戰略，構建符合 DT 時代的更創新靈活的『大中台、小前台』組織機制和業務機制。」其靈感常被歸因於芬蘭遊戲公司 Supercell 的「小團隊（cell）+ 強大平台支撐」模式。中台的定位是「支持多個前台業務且具備業務屬性的共性能力組織」；相對地，不具業務屬性的共性能力（中間件、資料庫、操作系統等）則稱為「平台」。

**理論基礎。** 阿里中間件首席架構師鍾華（花名古謙）在《企業 IT 架構轉型之道：阿里巴巴中台戰略思想與架構實戰》（2017）一書中，把業務中台的基礎定義為「共享服務體系」，本質是「回歸 SOA 的本質——服務重用」。書中提出共享服務的價值定位包括「服務可重用」「服務被滋養」等——例如「淘寶和天貓不必各自都開發一個評價服務」。此書起源於 2008 年阿里三大電商體系（1688、淘寶、天貓）架構完全獨立、重複建設的痛點。

**落地方法。** 業界共識是：業務中台以微服務架構落地，並採用領域驅動設計（DDD）進行領域建模——「通過劃分業務限界上下文邊界，構建中台領域模型，根據領域模型進一步指導微服務的拆分和設計」。DDD 的核心域／通用域／支撐域劃分，恰好對應核心中台／通用中台。因此「業務中台和微服務正是 DDD 實戰的最佳場景」。業務中台對前台提供的，是 API 接口級的業務服務能力（也可以是微前端的頁面級能力）。

**與數據中台的分工（與你的架構直接相關）。** 業務中台解決「業務能力重複建設與複用」；數據中台解決「數據的融合、共享與智能化應用」，提升數據利用效率與決策能力。阿里的數據中台方法論「OneData」把數據體系抽象為 OneModel（統一數據標準）、OneID/OneEntity（統一實體）、OneService（統一數據服務，「讓數據複用而非複製」）；OneData 曾把原先 30000 多個數據指標規範縮減為 3000 餘個。這與你把「跨源計算全部放在數據中台、業務中台透過 HTTP API 取用一層 curated 數據」的設計高度吻合——數據中台 owns 統一口徑與跨源計算，業務中台 owns 業務能力編排。

### 二、BFF（Backend for Frontend）

**起源。** BFF 一詞由 Phil Calçado 在 SoundCloud 工作時提出。SoundCloud 自 2013 年開始遷移至微服務架構時實際採用此模式；Calçado 於 2015 年 9 月 18 日在個人網站發表〈The Back-end for Front-end Pattern (BFF)〉一文正式描述，文首自述：「When I was at SoundCloud, being transparent about our architecture evolution was part of our technology strategy... our application of the Back-end for Front-end architecture pattern, or BFF。」此模式隨後由 Sam Newman 在其部落格與《Building Microservices》一書中推廣普及，Chris Richardson 的《Microservices Patterns》亦有討論。

**意圖與定義。** Sam Newman 指出，面對桌面 web 與行動裝置等多種 UI，傳統做法是提供「單一通用 API 後端」，但這會產生兩個問題：一是行動端與桌面端需要的呼叫次數、資料量差異巨大，通用 API 為了兼容而不斷膨脹；二是通用 API 服務多個前端，成為釋出瓶頸，並催生一個夾在中間、不聚焦任何業務領域的「中間團隊」。解法是「one backend per user experience」——每個使用者體驗一個後端。

**職責。** BFF 從下游多個微服務抓取資料，做聚合（aggregation）、裁剪（filtering）、轉換（transformation）、協定轉換（protocol translation）與視圖塑形，回傳「剛好符合該 UI 需求」的資料。Newman 舉電商願望清單為例：一次 BFF 呼叫可能觸發對 Wishlist、Catalog、Inventory 三個服務的呼叫，並在 BFF 內做並行編排與部分失敗降級。

**數量與團隊歸屬。** Newman 偏好「每種客戶端類型一個 BFF」（REA 模式）；SoundCloud 初期則讓 Android/iOS 聽眾 App 共用一個 BFF，但 SoundCloud 工程師事後表示若重新決策會傾向按平台拆分。準則是「one experience, one BFF」，且 Pete Hodgson 觀察 BFF 應沿團隊邊界對齊（康威定律）。BFF 通常由維護該使用者介面的同一團隊維護。

**真實案例。** 除 SoundCloud 外，Netflix 是經典案例：其 Edge 工程團隊（Daniel Jacobson 領導）從「resource-based / One-Size-Fits-All」的 REST API 轉向「experience-based API」，做法是讓各裝置團隊在伺服器端撰寫自己的「client adapter」，把「data gathering（由 API 平台負責）」與「data formatting/delivery（由各 UI 團隊在 adapter 內負責）」解耦——這正是 BFF 思想的另一種實作。Microsoft Azure Architecture Center 與 AWS 亦將 BFF 列為標準模式，並指出 GraphQL 是其替代/演進方案之一。

### 三、業務中台 vs. BFF 對照表

| 維度 | 業務中台（Business Middle Platform） | BFF（Backend for Frontend） |
|---|---|---|
| 抽象層次 | 應用／組織架構層面 | 技術架構層面 |
| 核心意圖 | 企業級業務能力複用、跨業務線沉澱共性能力、減少重複造輪子 | 為單一 UI 聚合／裁剪，解決過度抓取／抓取不足、降低前端複雜度 |
| 服務對象 | 多個前台／業務線／產品（一對多，內部類多租戶） | 單一前端類型（一對一，web 一個、mobile 一個） |
| 擁有／封裝什麼 | 核心業務領域模型、業務規則、可複用業務能力（訂單、用戶、支付…） | 聚合、轉換、視圖塑形、協定轉換；不擁有核心業務邏輯 |
| 建模方法 | DDD 限界上下文 + 微服務 | 面向特定 UI 的資料需求，輕薄編排 |
| 團隊歸屬 | 平台／核心團隊，服務多個產品團隊 | 前端／該客戶端團隊自己維護 |
| 在技術棧的位置 | 前台/BFF 之下、數據中台/基礎設施之上 | 特定前端之下、API 網關/業務中台之上 |
| 變更頻率 | 較穩定（沉澱資產） | 較高（隨 UI 快速變化） |
| 起源 | 阿里巴巴 2015 年「大中台、小前台」 | SoundCloud（Phil Calçado），Sam Newman 推廣 |

### 四、兩者如何共存（對 oingg.com 的建議架構）

在中台社群的實踐中，BFF 恰恰位於「API 網關與業務中台之間」。騰訊雲一篇廣受引用的文章描述其真實分層：作為應用服務層的 BFF「會從基礎業務服務如客戶服務、訂單服務、產品服務等微服務中獲取資料，進行一定的聚合和裁剪返回給某個具體業務線的前端應用」，而基礎服務層（即業務中台層）仍由後端團隊開發以確保品質；BFF 層則可由前端有興趣的同事用 Node.js/Go 開發。好未來（TAL）的數據中台實踐更是直接用 Node.js 做 BFF 層，把「複用性很差的 Controller」從後端拿到 BFF，讓「完成一個數據查詢功能」從牽涉數倉、後端、前端三方，縮減為前端與數倉兩方。

知乎一篇微服務 BFF 設計文章總結了兩者的協作關係與演進價值：「可以把大單體拆分成領域服務或者中台，通過 BFF……把中台和領域服務組合和編排成前端需要的 API，這樣中台和領域服務的變動也不會影響前端的用戶體驗。」

**對你的落地建議（見 Recommendations）**：數據中台（curated 數據 + 跨源計算）與業務中台（可複用業務能力 API）維持你目前的雙微服務；在其上，為 Vue web 端建立一個 Node.js/TypeScript BFF，未來若上行動端或開放 API，再各自新增 BFF。

### 五、常見誤區與重疊

1. **把 BFF 當成業務中台（或反之）**。最常見誤區。兩者抽象層次不同：一個服務多前台（中台），一個服務單前台（BFF）。有人用 GraphQL 實作的「統一 BFF 層」來類比中台，但這只是類比，本質仍不同。

2. **「胖 BFF」反模式**。當新需求不知該放哪個後端領域服務、各團隊互相推諉時，最可能的結果是「讓 BFF 負責幫忙組合各個服務的功能」，於是「BFF 朝著 ESB 的方向發展」，累積過多業務、甚至一個接口做多次寫操作而難保資料一致性。原則：BFF 應「關注在前端的體驗優化和領域中台服務能力的沉澱上，做好前後端的隔離」。

3. **「所有業務都可中台化」**。中台化的前提是企業已有「一定規模、多個業務、重複建設」的問題；中小企業或單一業務線盲目建中台，往往得不償失。有分析直言中台「不是萬能的，它只是企業數字化轉型的一種重要實現路徑」。

4. **把中台當成一套可外包、可購買的軟體**。36 氪《深氪》引述阿里雲前高管：「中台把客戶的期望值拉得太高了。中台既不是一套軟件，也不是一套服務器，而是一種理念、一套方法論，這最終導致客戶『接不住』。」第三方廠商銷售誇大，造成「中台能包治百病」的錯覺。

### 六、中台戰略的衰落與反思（重要背景）

- **VC 熱潮與元年**：2019 年被稱為「數據中台元年」，中台概念全面爆發。2019 年第四季度前後，三家中台服務商相繼宣布融資：滴普科技於 2019 年 9 月 24 日在北京發布會宣布 3500 萬美元 A 輪（由晨興資本、高瓴資本、IDG 資本聯合領投）、雲徙科技完成 3.5 億元 B 輪、袋鼠雲完成數億元 B 輪。

- **早期預警**：張勇早在 2019 年底湖畔大學分享時就發出方向性信號。演講原文接近「如果一個企業內部奔著中台做中台，也是死」，並強調「中台是沉澱出來的，不是從底下長起來的」；36 氪《深氪》則將其著名地轉述為「如果一個企業奔著中台做中台，就是死」。這為日後「拆中台」埋下伏筆。

- **2021 年轉向**：2021 年底，阿里從「大中台、小前台」升級為「多元化治理體系」；同期字節跳動於 2021 年 11 月 2 日由 CEO 梁汝波發全員信，按「緊密配合的業務和團隊合併為業務板塊，通用性中台發展為企業服務業務」的原則，成立六大業務板塊——抖音、大力教育、飛書、火山引擎、朝夕光年、TikTok，把原通用中台發展為企業服務業務（飛書、火山引擎）。「大廠拆中台」輿論四起。

- **2023 年徹底分拆**：2023 年 3 月 28 日，張勇發全員信啟動「1+6+N」組織變革。據《晚點 LatePost》2023 年 5 月獨家報導《運行八年後，阿里中台被彻底分拆》：承擔技術中台的 CTO 線一分為二——「『數據中台』獨立成了子公司愛橙技術，由阿里原 CTO 吳澤明（花名：范禹）任 CEO……自負盈虧；『業務中台』各團隊併入了淘天集團……按照具體業務如營銷、交易等，與原淘寶的技術線團隊合併」；組織中台的 HR、財務、市場等職能則分流到各業務集團。報導結論：「阿里『大中台』制度也終於成為了歷史。」

- **反思要點**：《21 世紀經濟報道》等分析指出中台失敗的常見原因，包括中台不熟悉具體業務、業務端各自又搭自己的中台（「在原先林立的煙囪上又套了中台的殼」）、中台的 KPI 與前台業務指標脫節導致「中台爛尾」，以及中心一旦過大「就會變得臃腫而效率低下」，甚至造成「創新窒息」。但多數評論同時強調：中台被拆並不否定其價值核心——「能力體系的複用，無論在什麼時候，都是具有價值的」，趨勢是中台「變薄」、與業務融合、向能力網絡演進。

## Recommendations

**階段一（現在，維持你的雙微服務）**：保持「數據中台（curated 數據 + 全部跨源計算）」與「業務中台（可複用業務能力 API）」的清楚分工。確保數據中台 owns 統一數據口徑（類比 OneService 的「數據複用而非複製」），業務中台只透過 HTTP API 取用、不自行做跨源計算——這條邊界要像 DDD 限界上下文一樣嚴格守住。

**階段二（新增 BFF 層）**：在業務中台之上、為 Vue web 前端建立一個**專屬的 Node.js/TypeScript BFF**（你最擅長的技術棧，正是 BFF 的理想語言）。BFF 只做：聚合多個業務中台/數據中台 API、裁剪成 Vue 頁面所需的 view-model、協定/格式轉換、前端專屬快取。由前端團隊（你）擁有，與 Vue App 同節奏釋出。

**階段三（多端時擴展）**：當出現第二種前端類型（行動 App、開放 API、第三方整合）時，**各自新增一個 BFF**，遵循「one experience, one BFF」。切勿讓 web BFF 兼服務行動端而變胖。

**必守的門檻／反模式警戒線**：
- **BFF 出現業務規則 = 紅線**。若你發現 BFF 裡開始寫訂單狀態機、計價規則、風控邏輯，代表該邏輯應下沉到業務中台或數據中台。這是「胖 BFF → ESB」退化的早期信號。
- **業務中台被單一前端的需求綁架 = 紅線**。若業務中台的 API 只為 Vue 頁面服務、充滿 UI 專屬欄位，它就退化成了偽 BFF，失去「多前台複用」的意義。
- **中台投資的規模門檻**：以你目前單一產品（oingg.com）而言，「業務中台」在此更接近「一個設計良好、以 DDD 建模的後端領域服務」而非阿里式的組織級中台——這完全合理。**不要為了叫它「中台」而過度投資組織級複用機制**；只有當你真正擁有多條業務線/多個產品共享同一批業務能力時，重量級業務中台的投資才會回本。這正是「拆中台」浪潮給中小團隊最重要的教訓。

## Caveats
- **抽象層次差異是所有比較的前提**：業務中台是應用/組織架構概念，BFF 是技術架構模式；把兩者當「二選一」是類別錯誤。它們在同一架構中扮演不同層。
- **中文語境的名詞混用**：中文技術圈常把「後台」「領域服務」「中台」「前台」混稱，且有「胖 BFF／瘦 BFF」之分；不同文章對同一層的命名不一致，閱讀時需看上下文。
- **「中台」在你的架構中是縮小版語意**：oingg.com 的「數據中台+業務中台」是借用中台術語描述雙微服務分層，與阿里集團級「大中台」在規模與組織意涵上不同——這對你反而是優點（避開了大中台的組織包袱）。
- **來源性質**：本報告的中台衰落敘事多來自中文科技媒體（晚點 LatePost、36 氪、21 世紀經濟報道）與個人技術部落格，部分含作者觀點與事後詮釋；阿里官方全員信對「中台」用語較委婉（「做輕、做薄」）。京東具體的中台裁員數字未能從一手來源證實，故本報告未列出具體數字。
- **BFF 的演進替代方案**：GraphQL 被 Microsoft、Phil Calçado 等視為 BFF 的替代或演進路徑（統一查詢層可減少對預定義 endpoint 的依賴）；你在選型時可評估，但對單一 web 前端而言，輕薄的 REST BFF 通常已足夠。
