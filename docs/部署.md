# 部署到 Cloud Run（GCP 專案 `oingg-bff`）

**狀態（2026-09-28）：前置設定已完成並驗證過，映像建置已在 Cloud Build 上實跑。** 見最後一節的紀錄。

還沒做的是**部署本身**（`gcloud run deploy`）與 Secret Manager 的那些 secret；下面的部署指令仍未執行過，
當成草稿讀。

## 為什麼是這個形狀

- **Dockerfile 是四階段的**：`deps`（裝相依＋`postinstall` 跑 `prisma generate`）→ `build`（tsc ＋
  tsc-alias）→ `prod-deps`（只裝 production 相依、跳過 postinstall）→ `runtime`（只有 dist ＋
  production node_modules ＋ package.json）。理由寫在 Dockerfile 的註解裡，改之前先讀。
- **沒有 `service.yaml`**：Cloud Run 可以完全用 `gcloud run deploy` 的旗標描述，多一份 YAML 就多一份
  會跟實際部署漂開的東西。等到有 CI 需要宣告式設定時再加。
- **不用本機 Docker build**：`gcloud builds submit` 在 Cloud Build 上建置，不需要本機 daemon，而且那也是
  將來 CI 會走的同一條路。

## 一次性的前置設定

**先確認 billing。** 沒有連上帳單帳戶的話，`gcloud services enable` 會以 `UREQ_PROJECT_BILLING_NOT_FOUND`
失敗，Cloud Build 與 Cloud Run 都不能用。2026-09-28 第一次嘗試連到 `01FD04-7E4E19-B46A81` 被拒絕
（`Cloud billing quota exceeded`——那個帳戶已經掛滿五個專案：gov／fundclear／tpex／twse／mops），
最後是使用者另開一個帳單帳戶 `018167-06139D-63AA6D` 才連上。

```bash
gcloud config set project oingg-bff
gcloud beta billing projects link oingg-bff --billing-account=<帳單帳戶>
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.com secretmanager.googleapis.com

# 存放映像的 Artifact Registry（asia-east1 = 台灣，跟使用者所在地一致）
gcloud artifacts repositories create bff \
  --repository-format=docker --location=asia-east1 \
  --description="oingg-bff-ts container images"
```

## 環境變數

`src/shared/env.ts` 的 `requireEnv()` 會在**啟動時**擋下缺少的變數（fail fast，不會跑到第一個請求才炸）。
以下 7 個缺任何一個，容器都起不來：

| 變數 | 內容 | 放哪裡 |
|---|---|---|
| `DATABASE_URL` | Neon Postgres 連線字串 | Secret Manager |
| `FILTERS_SERVICE_URL` | analysis-ts 的網址，**必須是 `https://`** | 環境變數 |
| `BFF_API_KEY` | 打 analysis-ts 用的 API key | Secret Manager |
| `FILTERS_SYNC_SECRET` | `POST /metrics/sync` 的共用密鑰 | Secret Manager |
| `API_DOCS_USER` / `API_DOCS_PASSWORD` | `/api-docs` 的 Basic Auth（**只在 production 生效**） | Secret Manager |
| `RESEND_API_KEY` | Resend 的金鑰 | Secret Manager |

選填、有預設值的：`PORT`（Cloud Run 自動注入，不要自己設）、`NODE_ENV`（Dockerfile 已設 production）、
`CORS_ORIGINS`、`EMAIL_FROM`（不設就是 `onboarding@resend.dev`，**只能寄到帳號本人信箱**）、
`BILLING_PAID_UIDS`、`FIREBASE_SERVICE_ACCOUNT_PATH`（見下一節）。

秘密一律用 Secret Manager，不要用 `--set-env-vars`——後者的值會出現在 `gcloud run services describe`
的輸出、Cloud Console 的服務詳情頁、以及部署指令的 shell 歷史裡。

```bash
# 每個秘密建一次，之後更新值用 versions add
printf '%s' 'VALUE' | gcloud secrets create DATABASE_URL --data-file=-
printf '%s' 'VALUE' | gcloud secrets versions add DATABASE_URL --data-file=-
```

## ⚠️ Firebase 憑證：這是唯一還沒決定的事

`src/infrastructure/firebase/client.ts` 現在是 `cert(serviceAccountPath)`，讀一個 JSON 金鑰**檔案**
（預設 `serviceAccountKey.json`）。容器裡沒有那個檔案，所以必須選一條路：

**A. 掛 Secret Manager 成檔案（不改程式）**

```bash
gcloud secrets create firebase-sa-key --data-file=serviceAccountKey.json
# 部署時：
#   --set-secrets=/secrets/firebase/key.json=firebase-sa-key:latest
#   --set-env-vars=FIREBASE_SERVICE_ACCOUNT_PATH=/secrets/firebase/key.json
```

**B. 改用 Application Default Credentials（改程式，但沒有長期金鑰）**

Cloud Run 服務本身就有一個 GCP 服務帳號身分，用它就不需要任何私鑰檔案存在任何地方。**但有一個要先確認的
前提**：Firebase 專案是 `oingg-web-dev`（2026-09-28 由 `oingg-web` 換過來，前端同時換），GCP 專案是
`oingg-bff`，**跨專案**。驗證 ID token 主要需要的是 Google 的公開憑證加上正確的 `projectId`，所以
`initializeApp({ projectId: "oingg-web-dev" })` 很可能就夠，但我沒有驗證過，而這是認證邊界——我不會在
沒有實測的情況下改它。

**換 Firebase 專案時要記得的兩件事**（2026-09-28 實際踩過）：`initFirebase()` 把 app 快取在模組變數裡，
所以換掉 `serviceAccountKey.json` 之後**不重啟程序等於沒換**；而 web API key 與服務帳戶必須屬於同一個
專案，否則 `security:check` 會以 sign-in 400 失敗。判斷金鑰屬於哪個專案不能看 `authorizedDomains`
（hosting 站名可以跟專案 id 不同名），要用 service account 簽一個 custom token 去兌換——跨專案會回
`CREDENTIAL_MISMATCH`。某個專案自己的 web API key 可以用服務帳戶直接取得，不必去 console 複製：
`GET https://firebase.googleapis.com/v1beta1/projects/<id>/webApps/-/config`。

**建議**：先用 A 把部署跑起來（不動認證路徑、風險最小），之後單獨一次改動處理 B 並實測登入。把「換掉認證
方式」跟「第一次部署」綁在一起，出問題時分不出是哪一邊造成的。

## 部署

```bash
gcloud builds submit --tag asia-east1-docker.pkg.dev/oingg-bff/bff/oingg-bff-ts:$(git rev-parse --short HEAD)

gcloud run deploy oingg-bff-ts \
  --image asia-east1-docker.pkg.dev/oingg-bff/bff/oingg-bff-ts:$(git rev-parse --short HEAD) \
  --region asia-east1 \
  --allow-unauthenticated \
  --set-env-vars FILTERS_SERVICE_URL=https://<analysis-ts>,FIREBASE_SERVICE_ACCOUNT_PATH=/secrets/firebase/key.json \
  --set-secrets DATABASE_URL=DATABASE_URL:latest,BFF_API_KEY=BFF_API_KEY:latest,FILTERS_SYNC_SECRET=FILTERS_SYNC_SECRET:latest,API_DOCS_USER=API_DOCS_USER:latest,API_DOCS_PASSWORD=API_DOCS_PASSWORD:latest,RESEND_API_KEY=RESEND_API_KEY:latest \
  --set-secrets /secrets/firebase/key.json=firebase-sa-key:latest \
  --min-instances 0 \
  --max-instances 4
```

`--allow-unauthenticated` 是必要的：web-nuxt 的瀏覽器端直接打這個服務，身分驗證是靠 Firebase ID token
在應用層做，不是靠 Cloud Run 的 IAM。

**`--min-instances 0` 有一個已知代價**：冷啟動時 `src/index.ts` 會先跑 `startMetricCatalogSync`
（向 analysis-ts 拉整份指標型錄）。那是 fire-and-forget、不阻塞啟動，但第一個請求可能打在型錄還沒同步完
的實例上。如果 `/metrics` 偶爾回空或舊資料，這是第一個要看的地方。

## 部署後要驗的

```bash
URL=$(gcloud run services describe oingg-bff-ts --region asia-east1 --format='value(status.url)')
curl -s "$URL/system/health"                      # appDb 應該是 ok
curl -s "$URL/metrics" | head -c 200              # 型錄同步成功了嗎
curl -s -o /dev/null -w '%{http_code}\n' "$URL/api-docs"   # production 應該是 401（Basic Auth）
```

`npm run security:check`（BOLA 掃描）2026-09-28 起可以跑了，六種 per-user 資源全部 PASS。唯一的 WARN 是
`/api-docs` 無認證可達——那是本機開發的已知缺口，**production 會被 Basic Auth 擋住，上線後要重跑一次確認
回 401**。

## 驗證紀錄（2026-09-28）

**做過了**：billing 連上、Cloud Build API 啟用、映像在 Cloud Build 上實際建置。過程中真正踩到的三件事，
按遇到的順序：

1. **帳單帳戶有專案數上限。** 連到 `01FD04-7E4E19-B46A81` 被拒（`Cloud billing quota exceeded`），因為那個
   帳戶已經掛滿五個專案。換成新開的 `018167-06139D-63AA6D` 才成功。**Cloud Run 也需要 billing**，所以這件
   事在部署路徑上，不只影響建置。
2. **新專案沒有自動配置 Cloud Build 服務帳戶。** 直接 `gcloud builds submit` 會回 `PERMISSION_DENIED`，
   即使呼叫者是 `roles/owner`。照 `oingg-twse` 的既有慣例建了
   `cloud-build-deployer@oingg-bff.iam.gserviceaccount.com`，先只給建置需要的
   `roles/cloudbuild.builds.builder` 與 `roles/logging.logWriter`（twse 那個還有
   `artifactregistry.writer` 與 `run.admin`，那是部署才要用的，等部署時再補），然後用
   `--service-account=projects/oingg-bff/serviceAccounts/cloud-build-deployer@oingg-bff.iam.gserviceaccount.com`
   送出。
3. **`.dockerignore` 漏放行 `pnpm-workspace.yaml`，第一次建置就此失敗。** 那份檔案帶 `allowBuilds`
   （pnpm 10+ 預設不跑相依套件的 build script，缺設定時 install 以 `ERR_PNPM_IGNORED_BUILDS` 回非零）與
   `blockExoticSubdeps: false`（uWebSockets.js 只在 GitHub 發佈）。`.dockerignore` 的「全部排除再放行」
   寫法本來就預期這種漏失會**立刻失敗而不是悄悄漏東西**，這次正是那個設計在起作用。

**Prisma 的 OpenSSL 警告可以忽略**：`prisma generate` 會印「failed to detect the libssl/openssl version」。
這個 schema 用的是 `provider = "prisma-client"`（Prisma 7 的無引擎產生器）配 `@prisma/adapter-pg` driver
adapter，runtime 不需要查詢引擎的原生執行檔，所以不必在映像裡裝 openssl。

**還沒驗證的**：容器**實際跑起來**（建置成功不等於 `node dist/index.js` 起得來）、Secret Manager 的掛載、
Cloud Run 的部署與冷啟動行為。上面的部署指令仍未執行過。

## 重跑建置驗證

設定檔是 repo 根目錄的 `cloudbuild-verify.yaml`（只 build、不推送映像，所以不需要 Artifact Registry）：

```
gcloud builds submit --project oingg-bff --region=global --config cloudbuild-verify.yaml --service-account="projects/oingg-bff/serviceAccounts/cloud-build-deployer@oingg-bff.iam.gserviceaccount.com" .
```

（原本這裡寫成用 `<(printf ...)` 組出設定，那是 bash 專用語法、在 PowerShell 跑不動——這台機器的主 shell
是 PowerShell，所以留一個檔案比省一個檔案實用。）

**兩個會誤導你的細節**：`gcloud builds submit` 上傳什麼由 `.gcloudignore` 決定（不是 `.dockerignore`），
改動前後請用 `gcloud meta list-files-for-upload` 確認私鑰沒被上傳；還有 `gcloud ... 2>&1 | tail` 的結束狀態
來自 `tail`，指令失敗時整條管線仍回 0，不要靠它判斷成敗，用 `gcloud builds describe` 另外查。
