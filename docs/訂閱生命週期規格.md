# 訂閱生命週期規格：到期提醒、寬限期、價格鎖定、退費

> 決策日 2026-09-24。適用於 `Subscription`（`prisma/schema.prisma`）與 `src/application/billing/`。
> 這份文件記錄的是**決定與理由**，不是實作狀態；還沒做的部分標為「未實作」。

## 0. 為什麼需要這份文件

反向試用與付費牆的骨架（Phase 0）已經上線，但整條生命週期裡有一段**沒有任何人負責**：使用者的
`currentPeriodEnd` 到了之後會發生什麼。對信用卡定期定額而言，金流商會自己扣款續命；對 ATM／超商的
一次性年繳而言，**金流商那邊沒有任何合約，到期就是到期**，而這條路徑依 vault 的
`中高齡族群支付行為與訂閱金流信任設計` 是「必備非選配」，還設了「若佔比 >20% 代表信任門檻仍是主要摩擦」
的監測線——也就是預期它是可觀比例，不是邊緣案例。

沒有提醒，這些人會在毫無預警下被降級。同一份研究說這族群「近半訂閱者訂了卻很少用、過半曾更換同類型
服務，對續訂價值敏感」——沉默到期約等於直接流失。

## 1. 兩條路徑，行為不同

`Subscription.renewalMode`（2026-09-24 新增）是唯一的判斷依據，**不要**用 `providerPeriodNo` 是否為 null
去推論：手動授予（`provider = MANUAL`）同樣沒有週期單號，會被誤判成自動續約。

| | `AUTOMATIC` | `MANUAL` |
|---|---|---|
| 付款方式 | 信用卡定期定額（藍新 `/MPG/period`） | ATM 虛擬帳號／超商代碼一次性年繳（MPG） |
| 金流商端合約 | 有，會自動扣款並回呼 | **沒有** |
| 到期時 | 自動續，除非扣款失敗 | 直接結束 |
| 前端文案 | 「下次扣款 <日期>」 | 「<日期> 到期，未續費將降級」＋續費入口 |

## 2. 到期前提醒

**`MANUAL`：到期前 30／7／1 天各一次。**
**`AUTOMATIC`：扣款前 7 天一次。**

依據與取捨：

- 年繳的業界共識是 30／7／1 三次（30 天給決定與準備付款的時間、7 天是行動提醒、1 天是最後一推）；
  超過三封會造成疲勞與退訂，少於一封則連合規與留存功能都失去。有來源指出提前三週提醒可讓續約率提升約 20%。
- **不要直接套用 dunning 的回收率數字**（常見說法是 40–70%）。那些講的是**信用卡扣款失敗**的非自願流失，
  前提是「可以重試」。`MANUAL` 不是扣款失敗，是根本沒有扣款機制，沒有東西可以重試，那組數字不適用。
- 真正可轉移的是「pre-dunning 優於 post-dunning」——在使用者還沒進入「出事了」心態前提醒，回收明顯較高。
  對我們更適用，因為我們**只有 pre 沒有 post**。
- `AUTOMATIC` 台灣目前無強制事前通知義務（見 §5），但 vault 把「不知情被扣」列為客訴監測指標，
  扣款前通知是針對這個族群的信任設計，不是多餘的禮貌。

## 3. 寬限期

**`AUTOMATIC`：到期後 7 天寬限 ＋ 扣款重試。**
**`MANUAL`：不設寬限。**

`MANUAL` 不設寬限不是苛刻，而是**這筆錢已經用別的方式付過了**。寬限期存在的理由是避免「churn by
friction」——突然斷線造成的摩擦性流失；而反向試用的平滑降級規則（見 `src/application/billing/quota.ts`）
已經保證「既有東西一律保留、只是不能新增」，沒有任何資料被刪除，使用者不會經歷突然失去。寬限期要買的
東西我們已經買到了，不該付兩次。寬限期過長反而會變成免費服務、降低續費動機。

`AUTOMATIC` 的寬限有意義，因為扣款可能在重試時成功——使用者本來就打算付錢，斷線純粹是技術意外。

降級後持續顯示「續費即可恢復」的入口，這是 `MANUAL` 的軟著陸手段，取代寬限期。

## 4. 價格變更與舊價保留

- 訂閱期內維持原價（不言可喻）。
- 調價**提前 60 天**通知。
- 舊價保留 **12 個月**，通知時就寫明結束日。**不做終身鎖價。**

vault 記錄 CMoney 用「終身價格鎖定」當留存武器，確實有效，但我們的處境不同：兩份市場研究都認為現行
NT$3,990 偏低（建議區間 NT$1,988–2,988 年費，或月 699／年 6,990），而 Van Westendorp 還沒做。
**現在承諾終身鎖價，等於把一個很可能定錯的價格變成永久負債。** 業界 2026 年的主流也是限期
grandfathering（12–24 個月）而非永久：永久鎖價會長出「第二份價目表」，讓之後每一次調價都被綁住，
並在計費、合約、財務流程裡累積營運負債。

## 5. 七天解約權——**需要律師確認，設計上先假設它適用**

台灣**目前沒有**自動續訂專法。只有《電子商務消費者保護綱領》第 3 點要求「如為自動續約應告知消費者」，
以及數位發展部的《零售業等網路交易定型化契約應記載及不得記載事項》。

但《通訊交易解除權合理例外情事適用準則》第 2 條的數位服務例外，要件是「非以有形媒介提供之數位內容，
或**一經提供即為完成**之線上服務，經消費者事前同意始提供」——立法理由舉的例子是電子書、線上防毒掃描、
匯款這類提供完就結束的東西。**年度訂閱是持續 12 個月的存取權，不是「一經提供即完成」**，所以這個例外
很可能不適用，也就是年繳預付**仍有七天無條件解約權**。

這不是工程能下定論的，但設計上的結論很清楚：**把七天無條件退費做進去**。法規風險先不論，對一個本來
就對自動續扣有戒心的族群，明示可退本身就是信任設計。Phase 1 要一起做退費路徑。

## 6. 實作狀態

已完成：
- `Subscription.renewalMode`（migration `20260924100000_add_renewal_mode_to_subscription`），
  預設 `MANUAL`——猜錯成 MANUAL 只是多寄一封提醒，猜錯成 AUTOMATIC 會讓人等一筆永遠不會來的扣款。
- `GET /billing/entitlement` 回傳 `renewalMode`、`currentPeriodEnd`、`trialEndsAt`，
  **前端現在就能做站上到期橫幅與試用倒數**，不需要任何新基礎建設。

未實作，且**刻意不先建**：
- 提醒的寄送與冪等紀錄。bff-ts 目前沒有排程器、沒有寄信供應商、也沒有部署管線，三者都缺的情況下先加
  欄位，是在替一個不存在的呼叫端建表。等寄送機制確定再加，屆時建議用 append-only 的
  `SubscriptionReminder(firebaseUid, kind, sentAt)` 而不是在 `Subscription` 上開三個布林欄位——
  提醒節奏改變時不必再 migration。
- `AUTOMATIC` 的寬限與重試：要等金流回呼（Phase 1）存在才有東西可以重試。
- 退費路徑：同上。

把「站上提示」和「主動觸及不回站的人」分開看是刻意的：前者零基礎建設、涵蓋所有會回站的人，現在就能做；
後者需要 email 供應商＋排程器＋公開 HTTPS 的部署環境，跟金流回呼的 NotifyURL 是同一批決定，應該一起做。
